## 二、已核实的事实（一手证据）

> 纪律：以下每条都有出处。**不要凭记忆改这些值** —— M1 阶段已因「信文档不信实测」踩过两次坑（`metadata.url`、`response_format`）。

### 2.1 Agnes keyframe 语义（官方文档核对）

| 事实 | 原文/依据 |
|---|---|
| `first_frame` / `last_frame` **至少提供一个** | 「与 `last_frame` 至少提供一个」 |
| 两个都给 = **首尾帧过渡** | 文档称「首尾帧控制」；示例 prompt：「人物从首帧姿态自然转身走向窗边，镜头缓慢推进并**平滑过渡到尾帧**」 |
| 语义方向 | **`first_frame` 决定从哪开始，`last_frame` 决定到哪结束**，中间是插值 |
| 保真度 | 「`keyframe` 会**尽量**将输入图片保持为成片的真实首帧或尾帧」← 是"尽量"，**不是像素级保证** |
| `reference` 不可用于接缝 | 「`reference` 将素材作为内容、风格、动作或节奏参考，**生成结果可能重新构图或重新安排时序**」 |

### 2.2 媒体 URL 约束

- 「所有媒体 URL 都应当可由 Agnes AI 服务公开访问。请避免使用**需要登录、带本地网络地址或即将过期**的链接。」
- **Agnes 没有上传接口** —— 官方文档全文核对，无 files / upload 相关内容。媒体输入只认公网 URL。

### 2.3 实测：Agnes 在**建任务瞬间**就预取图 ⚠️

用 `http://49.234.190.37/frames/<name>.png` 建真实任务，服务器 nginx access.log 记录到 4 次拉取，
其中**第一条与建任务响应同一秒**、UA 为 `Go-http-client/1.1`：

```
43.128.76.178 [12/Sep/2026:20:39:32 +0800] "GET /frames/probe-….png" 200 738049 "-" "Go-http-client/1.1"
```

**实现约束**：URL 必须在**建任务时就已经可访问**，不能是懒加载或稍后生成的地址。
→ 「抽帧 → 上传 → 建任务」的顺序不可颠倒、不可异步。

### 2.4 实测：上游产物 URL 长期有效

`platform-outputs.agnes-ai.space` 的产物 URL 复验（从 trace 日志取历史 URL 回取）：

| 类型 | 距今 | 结果 |
|---|---|---|
| 关键帧 png | ~3.0h | **200** · image/png · 743 KB |
| 关键帧 png | ~2.4h | **200** · 758 KB |
| 成片 mp4 | ~3.8h | **200** · video/mp4 · 1.01 MB |

→ 跨镜间隔只需 2–5 分钟，**富余充足**。`/api/image` 产出的图可直接当后续镜的输入 URL。

### 2.5 实测：首帧比例决定成片画幅（已第三次确认）

| 首帧尺寸 | 请求的 `aspect_ratio` | 成片 |
|---|---|---|
| 736×1312（9:16） | `9:16` | **704×1280** |
| 1024×1536（2:3） | `9:16` | **704×1088** |
| 736×1312（9:16） | `9:16` | **704×1280** |

→ `keyframeSizeFor()` 必须按目标画幅选尺寸，只写 `aspect_ratio` 不够。

### 2.6 实测：成片编码参数（**修正一处此前的错误记录**）

| 项 | 值 |
|---|---|
| 容器 | `mp4` (mov,mp4,m4a,3gp,3g2,mj2) |
| 视频 | `h264` / High / level 3.1 / `yuv420p` / **704×1280** / **24 fps** |
| **音频** | **`aac` LC —— 有音轨** |
| 码率 | 710 kbps – 1476 kbps（自适应，**同一分辨率下不固定**） |
| 时长 | 4.4583s / 5.1750s |

> ⚠️ **纠错**：此前记录与口头结论均称成片「无音轨」，**实测为错**。两个样本都带 AAC 音轨。
> Agnes 会自动生成环境声/音效，即使 prompt 未要求。这直接影响拼接的音频处理方案（见 §五）。

### 2.7 配额与队列实况

| 项 | 实测 |
|---|---|
| 生成配额 | **1 次/分钟（账户级）** —— 非分镜级，是全局冷却 |
| 排队时长 | 建任务成功后排队 ≈100s 才转 `running`；5s 成片总耗时 ≈2.5 分钟 |
| 队列满 | 上游回 `503 {"code":"video_queue_full"}` → 已识别为**可重试**（30s 建议等待），非硬失败 |
| 多镜成本 | 一条 5 镜片子光生成就 **5 分钟以上**，这是 M3 迭代成本的主要来源 |
| 时长下限 | 4 秒（本地已拦截，不浪费配额） |

## 三、跨镜接缝方案对比

### 3.1 符号约定

- `K_N` = 镜 N 的关键帧（由 `Shot.image_prompt` 经 `/api/image` 生成，**自带上游公网 URL**）
- `F_N` = 镜 N **成片的实际末帧**（需 ffmpeg 抽取，抽出后无公网 URL）
- `start_N` / `end_N` = 为镜 N 生成的起/止两张关键帧（拟定新增能力）
- 状态链既有约定：`start_state(N+1) = end_state(N)`（`schema.ts:117-120`）

### 3.2 四个方案

| # | 方案 | `first_frame(N+1)` | `last_frame(N+1)` | 接缝保证强度 | 关键帧消耗 | 外部基建 |
|---|---|---|---|---|---|---|
| **S0** | 现状（M1 已实现） | `K_{N+1}` | — | **无**（仅文字层状态链） | 1 张/镜 | 无 |
| **S1** | 单锚（真尾帧链） | `F_N`（抽帧） | — | **真实连续级** | 1 张/镜，但 `K_{N+1}` **作废** | 图床 |
| **S2** | 双锚（首尾帧控制） | `F_N`（抽帧） | `K_{N+1}` | **真实连续级 + 终点锚** | 1 张/镜（不浪费） | 图床 |
| **S3** | 共享端点帧 | `end_{N-1}`（**同一 URL**） | `end_N` | **锚定级**（同一张图钉死两侧） | **2 张/镜** | **无** |

### 3.3 两个关键洞察

**洞察 1 —— S2 的锚定区间天然很窄（这是它优于 S1 的实质理由）**

状态链本来就规定 `start_state(N+1) = end_state(N)`，所以 `F_N`（镜 N 实际末帧）
与 `K_{N+1}`（镜 N+1 的设计开场帧）**本就该是同一画面的两个近似**。
把两者同时喂给模型 = 给了一个很窄的锚定区间 → 模型运动幅度小、**不易崩**。

而 S1 把 `K_{N+1}` 丢掉不用 —— **S1 才是浪费关键帧的那个**。

**洞察 2 —— S3 的保证层次与 S1/S2 不同**

| | 接缝两侧是什么 | 保证层次 |
|---|---|---|
| S1 / S2 | 镜 N 的**真实末帧** | 真实连续（无跳变） |
| S3 | 镜 N+1 首帧 = `end_N` **原始 PNG**，但镜 N 的实际末帧只是"**尽量**"落在 `end_N` | **设计意图级**锚定 |

S3 无损（原始 PNG、无 H.264 压缩），但镜 N 的落点不精确 → 接缝处仍有**细微不连续**。
S1/S2 的 `F_N` 是真实末帧、无跳变，但图带**视频压缩损失**。**两者是不同层次的保证，不能互相替代。**

### 3.4 第 1 镜

**第 1 镜永远走 S0** —— 它没有前序成片可抽帧，也没有 `end_0`。
例外：若采用 S3，第 1 镜可写 `last_frame = end_1`，`first_frame = start_1`（首次即双锚）。

## 五、ffmpeg 拼接方案（已实测）

### 5.1 实测结果

用两个真实成片（4.4583s + 5.1750s）做 concat demuxer 测试：

| # | 方式 | 产物大小 | 帧数 | 时长 | 音频 | 警告 | 解码 |
|---|---|---|---|---|---|---|---|
| A | `-c copy`（全流拷贝） | 1,281,426 B | 231（=124+107 ✅） | 9.664s | 304 帧 / 32 kHz | ⚠️ **DTS 非单调** | ✅ 无错 |
| B | **`-c:v copy -c:a aac`** | **1,277,185 B** ← **最小** | 231 ✅ | 9.678s | 418 帧 / 44.1 kHz | **✅ 无** | ✅ 无错 |
| C | 全重编码 libx264 CRF18 + AAC 128k | 2,171,256 B（**+70%**） | 231 ✅ | 9.678s | 418 帧 / 44.1 kHz | ✅ 无 | ✅ 无错 |

**方案 A 的警告**（音频流时间戳）：
```
Non-monotonic DTS; previous: 165888, current: 165600; changing to 165889.
This may result in incorrect timestamps in the output file.
```

**方案 B 是意外的最优解**：视频流拷贝（零画质损失）+ 音频重编码，
**既消掉了 DTS 警告，体积还比 A 更小**（原音轨是 32 kHz，重编码到 44.1 kHz/128k 反而更省）。
且完全绕开了重编码视频的 70% 体积代价。

### 5.2 推荐策略

1. **默认方案 B**（`-c:v copy -c:a aac -b:a 128k -ar 44100 -ac 2`）—— 视频无损、音频干净、体积最小。
2. **首次尝试 A**（`-c copy`）仅在需要极限速度时用；一旦出现 DTS 警告立即切 B。
3. **兜底方案 C**（全重编码）—— 仅当各镜**视频**参数不一致（分辨率/帧率/像素格式/SAR）时降级。
   用 `ffprobe` 先比对，不一致才重编码；**不要无条件重编码**。
4. **音频仍有一个产品决策未定**：各镜音轨是模型各自生成的环境声，硬切处**音量/音景可能突变**。
   待决：硬切（当前默认）/ 短交叉淡化 `acrossfade`（需全重编码音频，放弃流拷贝）/
   丢弃各镜原声、整片重新配 BGM。**技术默认形态已确定（方案 B），产品层面待拍板。**
5. **时长偏差**：实测 9.664–9.678s vs 理论 9.633s（+0.03~0.045s）。拼接后总时长校验要留容差。
6. **产物落地**：`.data/artifacts/<runId>/final.mp4`，同步更新 `manifest.json` 与既有 `/api/export` 归档逻辑。

## 六、推荐路线

> 顺序原则：**先把零配额的做完**。拼接是纯本地工程，跨镜接缝要烧配额 —— 先做便宜的，且拼接与接缝解耦（接缝改方案不影响拼接流水线）。

### 阶段 1：M3a 拼接（零配额，可离线验证）

1. **统一各镜参数检查**：`ffprobe` 比对 → 决定 `-c copy` 还是重编码
2. **lib 层封装** `lib/concat.ts`：`probeShot()` / `planConcat()` / `concatShots()`（纯函数优先，可单测）
3. **端点** `api/concat`：入参 runId 或 shots，产出 `final.mp4`
4. **UI 触发**：时间轴尾部「拼接成片」按钮 + 进度
5. **验证素材**：现有 2 个 artifact 的 mp4 可反复离线测，**不烧任何配额**
6. **音频策略定案**（需产品决策，见 §7.4）

### 阶段 2：M3b 跨镜接缝（烧配额）

**次序建议：先 S3（零基建）验证效果，接缝不够再上 S2。**

理由：S3 不需要任何新基建即可跑通，先用最小成本拿到「接缝到底够不够」的实证；
若实测证明锚定级不足（肉眼可见跳变），再投入图床 + 抽帧实现 S2。

> 注意：**工程兜底应默认站在 S3 一侧**。若要长期依赖 S2，则「服务器可用性」与「scp 凭据」会变成运行期硬依赖（见 §八）。

## 八、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **服务器可用性** | 若走 S2，服务器挂了则接缝链路断，M3 无法出片 | 工程默认 S3；S2 作为可选增强 |
| **图公开可访问** | 任何知道路径的人都能看图 | 文件名掺 hash；已实测目录 403 不可枚举 |
| **运行期 SSH 依赖** | scp 上传需要本机 SSH 凭据可用 | 若采用，需明确降级路径（失败则退回 S0 单镜模式，不阻断拼接） |
| **磁盘增长** | 服务器 frames/ 与本地 `.data/` 只增不减 | 加轮转/清理策略（按 runId 或时间） |
| **配额成本** | 一条 5 镜片子 ≥5 分钟；M3 迭代成本显著高于单镜 | 拼接用离线素材验证；接缝验证攒批做，别零敲碎打 |
| **音频瑕疵** | `-c copy` 的 DTS 非单调警告 | 页面真听验证；必要时接缝处重编码 |
| **文档与现实偏离** | `15` 号文档 `:253` 仍写主引擎 Kling 2.1，实跑 Agnes Video 2.5 Flash | 一并对齐 |

---

## 九、一句话总结

**M3 = 拼接（纯本地、零配额、已实测可行）+ 跨镜接缝（要烧配额、方案待定）。**
先做拼接拿到「多镜 → 一条片子」的可见产物，再接缝；接缝先试零基建的 S3，不够再上 S2。
