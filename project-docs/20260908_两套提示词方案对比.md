## 一、商品推广对比

**goodcase 案例（Lavinia）原文是 765 字符的单段英文自然句**：一段话讲完整叙事（瑕疵特写→疲惫工作→拿瓶→滴管特写→涂抹→变水光肌→微笑收尾），无分镜编号、无节拍、无负面词，靠模型自己剪辑（"smooth cinematic cuts"）。稳定分 90 = 这条 prompt 复现方向很稳。

**video-flow 输出**：风格规格（8 个 keywords_en + 5 色 palette）→ 实体档案（人物/瓶身/液滴三实体带基准朝向）→ 3 镜，每镜含 image_prompt / video_prompt / 秒级节拍 / 转场动势设计 / 负面词。

| 维度 | 单段式（goodcase 案例式） | 分镜式（video-flow） |
|---|---|---|
| 信息密度 | ~765 字符，模型自由发挥空间大 | 每镜 ~1500 字符 × 3，逐秒受控 |
| 可控性 | 低（叙事对但细节靠运气） | 高（方位锁定/状态链/匹配剪辑转场/CTA 留位） |
| 出片成本 | 一次调用出整片 | 逐镜生成 + 尾帧链拼接 |
| 失败半径 | 整片重来 | 单镜重试 |
| 适合 | 快速出片、模型对单段 prompt 稳定性高（Seedance 整片模式） | 换模型不挑食、多镜长片、精确节奏要求 |

**结论：商品推广场景，两套互补。** 案例证明 Seedance 类模型对单段 prompt 已经很稳，5-15s 短广告用单段式性价比更高；分镜式的价值在长片、精确节奏（秒级节拍）和跨镜一致性锁（方位/朝向不翻转）。建议给系统加一个**「整片单 prompt」压缩导出**（把分镜卡压回 ~800 字符单段），一条 brief 两种格式都出，投不同模式。

## 二、App 推广对比（发现范式级差异）

**goodcase 案例的正确范式是「真实 UI 录屏」**：固定机位拍真实 Windows 11 桌面，浏览器框架、书签栏、任务栏、播放器控件全部像素级锁定不动，**只有视频画布区域在动**（里面放一段时尚短片）。App 本体是真实运行的 localhost 页面截图，AI 不负责渲染 UI。

**video-flow 输出**是电影感分镜：2 镜（点播放 → 拖进度条），有实体档案和秒级节拍，但 UI 只能描述到"深紫色画布、浅紫进度条、白色图标"这个粒度——**视频模型生成不出像素级一致的 UI 和可读文字**，生成出来的"播放器界面"必然是糊的假 UI。

**结论：App 推广的"功能演示"场景，video-flow 现在的分镜范式是错配的。** 正确路线：
1. **UI 演示** → 真机录屏 + AI 局部动效（案例范式），prompt 里锁 UI 不动、只让画布动；
2. **品牌情绪片**（不讲 UI 讲感觉）→ video-flow 的分镜范式完全胜任。

建议系统在需求识别到"App 演示"类 brief 时提示用户走录屏路线，或新增「录屏保真模板」（锁 UI + 动效区域分层描述）。

## 三、video-flow 输出发现的真实瑕疵

1. **风格关键词注入重复**：`keywords_en` 的 "clean ivory background" 与场景描述里的 "clean ivory background" 在 image_prompt 中逐字出现两次（verbatim 注入无去重）。短词表无伤大雅，词表大了会稀释有效信息。**建议：注入前对已出现的关键短语去重。**
2. **video_prompt 偏长**（~200 词，超出规则 40-80 词）——verbatim 实体档案 + 状态链 + 全量关键词叠加导致。生成模型对超长 prompt 的遵循度会下降，考虑把实体档案压缩为「本镜相关字段」而非全文注入。

## 四、附带修复（本日落地）

- `src/lib/llm.ts`：新增**通用 400 降级**——实测 lanfengai 对 `temperature+response_format+reasoning_effort` 组合返回不带参数名的 `invalid_request`，原降级逻辑匹配不到。现在通用 400 会逐级剥离 response_format → reasoning_effort 重试（探针 5 组参数二分验证：单项均 200，组合 400）。
