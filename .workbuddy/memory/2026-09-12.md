## 修正：生成限流 ≠ 查询限流（用户指出，已改）

**用户指正**：「生成视频的间隔是一分钟以上，不是查询的时间间隔是一分钟」。上一版把两类调用塞进同一个闸门，是个真 bug。

### 一手证据（直连上游 `/agnesapi` 实测）

| 查询间隔 | 样本 | 结果 |
|---|---|---|
| 1.2s | 4 次 | 全 200 |
| 2.0s | 8 次 | 第 4、8 次 429，`Retry-After: 2`，body `too many video status queries` |

### 两个真实网关行为差异（都要靠实测，不能信文档）
1. **`response_format: "b64_json"` 会让网关不再返回 `url`**。而路由原本固定先要 b64 → `preferUrl` 形同虚设。
   改为：`preferUrl` 时 attempts = `["auto", "url"]`（**不发** `response_format`，拿默认返回）。
2. **keyframe 模式下成片画幅由首帧图决定**，请求里的 `aspect_ratio` 被弱化：
   1024×1536（2:3）首帧 → 成片 **704×1088**；720×1280（9:16）首帧 → 成片 **704×1280**。
   网关把边长吸附到 64 的倍数（720→704 正常，比例是对的）。

### 顺手优化
`preferUrl && 有 url` 时**不再回传 b64**：关键帧是 MB 级，实测响应体 **1.76 MB → 206 B**。

## 更正：尾帧链 A/B 方案的表述有方向性错误（用户追问「ab 方案有什么不同」）

**上一轮把 B 描述反了，作废。** 原表述「B = 本镜关键帧作 first_frame + 上一镜尾帧作 last_frame」——按官方文档语义，这会让**本镜倒着走回上一镜的结尾**，是错的。

### 一手依据（Agnes Video 2.5 Flash 官方文档实测抓取）

- `first_frame` / `last_frame` **至少提供一个**（不是必须同时）。
- 两个都给 → 官方称「首尾帧控制」，示例 prompt 措辞：「人物从首帧姿态自然转身走向窗边，镜头缓慢推进并平滑过渡到尾帧」→ **明确是首尾帧之间的过渡/插值**，不是自由演化。
- `aspect_ratio: 9:16` 官方标称输出 `720x1280`（实测成片 704×1280，网关吸附 64 倍数）。
- **所有媒体 URL 必须公网可访问**，且在任务完成前保持有效。

### 修正后的三个方案（S0 是当前已实现形态）

| 方案 | first_frame | last_frame | 含义 |
|---|---|---|---|
| **S0 现状（M1 已实现）** | 本镜关键帧 K_{N+1} | 无 | 画面起点由本镜关键帧决定，构图可控；跨镜**只有文字层状态链**，视觉层无约束 |
| **S1 单锚（真尾帧链）** | 上一镜成片末帧 F_N | 无 | 接缝真接上；但本镜关键帧**白生成**，且**误差累积**——每步小偏差滚雪球，景别/构图不再受控 |
| **S2 双锚（首尾帧控制）** | 上一镜成片末帧 F_N | 本镜关键帧 K_{N+1} | 起点接缝 + 终点钉回本镜设计构图，**漂移有刹车**；关键帧不浪费（仍被用作终点锚） |

**关键洞察**：状态链本来就规定 `start_state(N+1) = end_state(N)`，所以 F_N 与 K_{N+1} **本就该是同一画面的两个近似** → S2 的双锚区间天然很窄，模型运动幅度小、不易崩。这也是 S2 优于 S1 的实质理由（S1 才是浪费关键帧的那个）。

**S2 的代价**：`image_prompt` 现在按「这一镜开场画面」写，改作终点锚后 prompt 工程要跟着调语义；且首尾差异大时会出现生硬形变/两段式跳变。

### 新发现的前置阻塞（S1/S2 共同）

**ffmpeg 抽出的末帧没有公网 URL。** 文档要求媒体 URL 公网可访问，而项目现在
**无 `public/` 目录、无上传端点、无静态托管**（`src/app/api/` 仅 export/image/llm-configs/logs/shot/shots/style/video 八个 route）。
→ 抽帧后必须先解决「本地帧 → 公网 URL」，否则 S1/S2 都跑不通。这是 M3 需要的第一个新能力。

**第 1 镜永远走 S0**（无前序成片可抽帧）。

### 关键实现决策（已钉死）
