## 修正：生成限流 ≠ 查询限流（用户指出，已改）

**用户指正**：「生成视频的间隔是一分钟以上，不是查询的时间间隔是一分钟」。上一版把两类调用塞进同一个闸门，是个真 bug。

### 一手证据（直连上游 `/agnesapi` 实测）

| 查询间隔 | 样本 | 结果 |
|---|---|---|
| 1.2s | 4 次 | 全 200 |
| 2.0s | 8 次 | 第 4、8 次 429，`Retry-After: 2`，body `too many video status queries` |
| 3.0s | 10 次 | 全 200；但应用层 3.5s 跑 6 次仍偶发 1 次 429（非确定性） |

## M1 闭环：关键帧 → I2V（用户：接下来的目标是什么 → 接通关键帧→I2V）

### 两个真实网关行为差异（都要靠实测，不能信文档）
1. **`response_format: "b64_json"` 会让网关不再返回 `url`**。而路由原本固定先要 b64 → `preferUrl` 形同虚设。
   改为：`preferUrl` 时 attempts = `["auto", "url"]`（**不发** `response_format`，拿默认返回）。
2. **keyframe 模式下成片画幅由首帧图决定**，请求里的 `aspect_ratio` 被弱化：
   1024×1536（2:3）首帧 → 成片 **704×1088**；720×1280（9:16）首帧 → 成片 **704×1280**。
   网关把边长吸附到 64 的倍数（720→704 正常，比例是对的）。

### 顺手优化
`preferUrl && 有 url` 时**不再回传 b64**：关键帧是 MB 级，实测响应体 **1.76 MB → 206 B**。

| R6.1 | 交付 = 成片文件 + 预览 URL + 关键帧 + 风格 JSON | ⚠️ prompt/JSON 导出齐；**成片 mp4 无归档/打包下载** |

其余（R1.1 / R2.1-2.4 / R3.1 / R4.1-4.3 / R5.2 / R5.3 / R6.2）均已满足；R4.1 实测成片 4.46s < 10s。

**关键架构发现**：`lastFrame` 通路已全程铺好（`video-providers.ts:72` 支持 `last_frame`、`api/video/route.ts:39` 收参、`use-video-tasks.ts:46` 有类型），
但 `video-payload.ts:25` **只传 firstFrame，从不传 lastFrame** —— 即「尾帧链」在**文字层**（end_state 状态链）成立，**视觉层完全没接**。
这是跨镜一致性最实质的缺口，也是 M3「首尾帧 chain」的核心工作量（需 ffmpeg 抽上一镜尾帧）。

**待决**：下一步走 M1 封板（补 4 项 + 写验收记录）还是直接进 M3（尾帧链 / ffmpeg 拼接）。M2（幂等/Postgres checkpoint/长任务 suspend）按文档 :274 的前提是「<10s 单镜」，与当前多镜实况不符，暂不建议。

### 新发现（重要）
- **上游 503 `video_queue_full`**：免费档是**排队制**，队列满直接拒绝建任务
  （`{"code":"video_queue_full","message":"video queue is full, please retry later"}`）。
  首次建任务就撞上，等 35s 重试即成功。**处理**：`video.ts` 识别该 code → 给 30s 建议等待
  （`QUEUE_FULL_RETRY_MS`）+ 明确 message，前端据此排全局冷却，而不是当硬失败逼用户手点。
  **教训：不要只看 HTTP status，要读上游的 code 字段**。
- **排队时长真实体感**：建任务成功后排队 ≈100s 才转 `running`；5s 成片总耗时约 2.5 分钟。
  5 镜片子光生成就 5 分钟以上 —— 这是 M3 多镜迭代成本的主要来源。
- **首帧比例决定成片画幅**（再次确认）：同一 `aspect_ratio: "9:16"`，2:3 首帧 → 704×1088；
  9:16 首帧 → 704×1280。
