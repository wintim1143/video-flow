## 环境踩坑（重要，跨项目可复用）

1. **WorkBuddy broker 沙箱会拦截 node 子进程的 rename/mkdir**（node-brokered-fs-shim，CODEBUDDY_BROKER_DENY）：
   - `npm install` 卡死在 bin link 阶段（几十分钟无进展即此因），错误 `rename node_modules/.bin/jiti -> .jiti-xxx`。
   - Next dev server 无法 `mkdir .next`（写 /tmp 也被拒），500。
   - 对策：**重活（npm install / next dev）让用户在自己的终端跑**；agent 侧只做代码验证（tsc --noEmit、纯函数 node 测试）。
   - `~/.workbuddy/settings.json` 的 `sandbox.extraAllowWrite` 加入项目路径后，shell 命令可写项目目录，但 node 子进程 shim 不一定生效（本次未生效）。
2. **网络极慢**（~65KB/s）：npm 全量安装 30+ 分钟不可行；改用「缓存已有 + 手动 ln -s 重建 .bin」让 tsc/next 可执行。
3. next 包解压残缺（缺 index.d.ts/types/）→ dlopen 原生 swc 报 `code signature invalid (errno=85)` → Next 回退下载 wasm。残留问题，用户本地 npm install 重装即愈。
4. 用户终端跑法：`npm install && npm run dev`（.env.local 已建占位，填 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL）。

## 分镜慢/失败根因与两段式改造（用户第六轮需求）

- **根因实测**：原 5 镜一次生成 300s 超时 0 字节。usage 显示 gpt-5.6-terra 是推理模型（reasoning_tokens 1753 > 可见输出 670），原请求要吐 3000+ token ≈ 8-10 分钟，必然超时；"失败好多次"= 时好时坏。中转站 prompt_tokens 填充严重（4400 vs 实际 ~1500）。
- **两段式改造**：大纲（小输出，含 global_negative/consistency_notes）→ 逐镜展开（并发 2 流水线，start 由服务端按大纲累加、不信 LLM 算术；单镜失败重试 1 次后标记跳过）→ SSE 全程推送 trace/outline/shot/shot_error/done 事件；前端进度条 + 每镜耗时 + 「重试第 N 镜」按钮（新端点 /api/shot 定点重试）。
- **reasoning_effort 关键优化**：中转站支持 `reasoning_effort:"minimal"`，单镜 118.4s → 18.7s（6 倍），质量四项全绿；low 会挂起（120s 超时），勿用。chatJSON 降级队列：全量 → 剥 reasoning_effort → 剥 response_format（按 400 报错特征）。profile.reasoningEffort 可配（""=关闭，缺省 minimal）；env 回退读 LLM_REASONING_EFFORT。
- **zod 3.25 泛型坑**：带 .catch()/.default() 的 schema Input≠Output，chatJSON 的 `z.ZodType<T>` 会把 T 推断成 Input（字段 unknown）——修法 `z.ZodType<T, z.ZodTypeDef, unknown>`。另 ShotSchema.start 加 .catch(0)（逐镜模板不让 LLM 输出 start，coerce undefined→NaN 会炸）。
- **安全事件（已化解）**：用户把真实 key 填进会被提交的 llm.config.example.json（a4dab88 提交时还是占位符，未泄露）；已把真实配置移入 gitignored llm.config.json（terra+minimal / deepseek 备选），example 恢复占位符，README 加警示。
- 实测速度：大纲 94s（中转站吞吐波动仍大）+ 5 镜并发 2 ≈ 全程 2-3 分钟；成本：总调用 1+N 次，token 略增但成功率与体验质变。

## 跨镜连续性改造（防"车头翻转"式错位）

- 问题：逐镜独立生成，仅锁风格 keywords_en 与 consistency_notes（产品属性），没锁主体在空间中的状态（朝向/光源/时间），镜间车头朝向翻转。且并发 2 下靠"前镜生成结果"衔接不可靠（镜3开跑时镜2可能未完成）。
- 方案：状态链放进大纲（单次顺序调用，全局视野，不依赖生成顺序）：
  1. Outline 新增 entities（实体档案：name_zh + 锁定 descriptor_en，含朝向基准约定）与每镜 start_state/end_state（硬规则：镜N end_state = 镜N+1 start_state，未经转场禁止翻转朝向）。
  2. shotDetail prompt 注入实体档案 + 上一镜末状态 + 本镜状态链，硬规则：image_prompt 严格等于 start_state、video_prompt 从 start_state 演化到 end_state。
  3. Shot 新增 start_state/end_state 字段（catch("") 兼容旧数据），服务端强制用大纲值覆盖；ShotRow 顶栏下新增「状态链：镜首 → 镜末」可视化条。
- 探针验证 8/8：实体/状态注入、接续指令、旧数据兼容。tsc 全量干净。
